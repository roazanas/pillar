# Как довести Pillar до законченного языка

Аудит от 31 октября 2026 года. Исходная ревизия: `a4815369c9080d481ac13b649b786a959d4993e5`.

## Вывод

У Pillar уже есть работающее ядро: вертикальная запись, выражения с приоритетами,
функции, рекурсия, ветвления, циклы, числовой ввод-вывод и генерация нативного кода.
Все пять примеров работают после подготовки runtime под текущую платформу.

Следующая цель — определить и реализовать небольшой, последовательный язык:
объявленные типы действительно проверяются, области видимости предсказуемы,
корректная программа компилируется, а ошибочная получает понятную диагностику.
Новые возможности стоит добавлять поверх этого основания.

Рекомендуемое направление: компактный статически типизированный язык с вертикальным
исходником, удобным редактором и нативной компиляцией. Название, короткие ключевые
слова и вертикальную запись можно сохранить. Они задают характер проекта.
Cranelift, Logos и Chumsky уже выполняют нужную работу; оснований менять их по
результатам этого аудита нет.

## Что проверено

- В исходном checkout `cargo build --bin plrc --locked` завершается ошибкой:
  `Cargo.lock` содержит версию пакета `0.4.0`, а manifest — `1.0.0`.
- После автоматического согласования lock-файла обычным `cargo test`
  `cargo build --bin plrc --locked` проходит.
- `cargo test --all-targets` — успешно, но **0 тестов**.
- `cargo fmt --all -- --check` — успешно.
- `cargo clippy --all-targets --locked -- -D warnings` — успешно.
- 29 отдельных сценариев компиляции, включая обычные и ошибочные программы.
- Проверены результаты пяти примеров: `fact(5)` → `120`, `fib(10)` → `55`,
  `mult` → все 100 произведений, `test` → `5`; для `complex` при вводе
  `6, 2, 2.0, 0.0` получены `6, 4, 3, 1, 1, 1, 12.5664, 32`.
- Все пять существующих `.plr` также отдельно скомпилированы.

Проверки выполнялись на macOS ARM64, Rust 1.96.0. Исходники компилятора и
репозиторный `runtime.o` не изменялись. Изменение версии в `Cargo.lock`, сделанное
Cargo при проверке, отменено; исходный lock-файл сохранён. Для запуска программ `runtime.c` был
скомпилирован в отдельный временный каталог, из которого запускался `plrc`.
Дополнительно был явно выбран SDK Xcode 26.5: установленный по умолчанию SDK 27
оказался несовместим с локальным линкером. Это отдельная особенность окружения.
Linux и Windows в этом аудите не запускались.

## Подтверждённые проблемы

Примеры ниже показаны в горизонтальном представлении `.rplr`. Для текущего
компилятора их нужно сначала преобразовать через `plrc -t`.

### 1. Аннотации локальных переменных теряются

В `src/parser.rs:272` `_typ` отбрасывается, а `Statement::Let` не содержит типа.
В `src/compiler.rs:251` тип берётся из результата вычисления инициализатора.

```text
FN main() {
  LT x: int = 1.5~
  OUTF x~
  RET 0~
}
```

Компилируется и печатает `1.5`. Аналогично `LT x: bool = 123~` принимается.
Если язык статически типизирован, обе программы должны получать ошибку до codegen.

**Изменение:** сохранять аннотации в AST, добавить проверку типов, передавать
в backend уже проверенное представление программы.

### 2. Сигнатуры функций не согласованы

В `src/compiler.rs:36` все функции получают результат `I64`. В местах вызова
(`:197` и `:321`) все параметры повторно объявляются как `I64`, хотя определения
поддерживают параметры `float` и `bool`.

```text
FN f(x: float) { RET 0~ }
FN main() { f(1.5)~ RET 0~ }
```

Результат: panic из-за несовместимых сигнатур. То же происходит с `bool`.
`RET 1.5~` в функции приводит к ошибке верификатора и panic.

**Изменение:** сначала собрать таблицу всех функций с настоящими сигнатурами,
проверить тела и вызовы, затем объявить функции в Cranelift и скомпилировать тела.
Это также даст нормальные ошибки неизвестной функции, числа аргументов и
повторного определения. Прямые и взаимные вызовы целочисленных функций уже могут
работать через текущие import-декларации; проблема шире поддержки forward calls.

### 3. `RET` внутри `WH` ломает построение IR

```text
FN main() { WH true { RET 7~ } RET 0~ }
```

Результат: `you cannot add an instruction to a block already filled`.
В `src/compiler.rs:359` результат `compile_stmt` игнорируется, затем после
завершившего блок `return` добавляется `jump`.

**Изменение:** явно представлять результат генерации блока: продолжает выполнение
или завершён. Прекращать генерацию после терминатора. Для `IF`, обе ветви которого
завершаются, также корректно передавать это состояние наружу.

### 4. Нет областей видимости блоков

Все локальные имена функции хранятся в одной `HashMap`.

```text
FN main() {
  LT x: int = 10~
  IF true { LT x: int = 20~ }
  OUTI x~
  RET 0~
}
```

Печатает `20`. При обычной блочной области видимости ожидается `10`.
Если запретить shadowing, нужна ошибка объявления. Текущее поведение необходимо
либо специально описать как семантику языка, либо исправить.

Более опасный случай:

```text
FN main() {
  IF false { LT x: int = 42~ }
  OUTI x~
  RET 0~
}
```

Компилируется и печатает `0`: имя доступно вне блока, хотя его инициализация
не выполнялась. Нужны разрешение имён, стек областей видимости и анализ
гарантированной инициализации.

### 5. `EL` и блок после него необязательны независимо

В `src/parser.rs:298` и `:299` отдельно применены два `or_not()`.

```text
FN main() { IF false { OUTI 1~ } { OUTI 2~ } RET 0~ }
```

Принимается и печатает `2`, хотя `EL` отсутствует.
`IF false { OUTI 1~ } EL RET 0~` также принимается: после `EL` нет блока.

**Изменение:** необязательной должна быть целая пара `EL + block`.

### 6. Правила операторов и чисел неполные

| Сценарий | Фактический результат |
| --- | --- |
| `OUTI !2~` | Печатает `3`: реализован XOR с единицей |
| `IF 1.0 { ... }` | Ошибка верификатора, затем panic |
| `OUTF 1.0 + 1~` | Ошибка верификатора, затем panic |
| `IF 1 == 2 < 3 { ... }` | Ошибка верификатора; равенство и сравнение имеют одинаковый приоритет |
| `OUTI -9223372036854775808~` | Ошибка лексера на минимальном значении `i64` |
| `OUTI 9223372036854775807 + 1~` | Печатает `-9223372036854775808` |

Переполнение само по себе может быть допустимой политикой языка, но её нужно
описать. Для `!` следует либо требовать `bool`, либо определить truthiness и
использовать сравнение с нулём. Не стоит молча выбирать поведение по типу левого
операнда в backend.

### 7. Ошибки исходной программы приводят к panic

Неизвестная переменная вызывает `panic!`, строковый литерал — `todo!`, неизвестная
функция доходит до линкера. Ошибки присваивания и верификатора превращаются
в panic через `expect` в `main`.

**Изменение:** структурированные ошибки с кодом, сообщением и исходным диапазоном.
Ошибки пользователя завершают процесс с понятной диагностикой. Внутренняя ошибка
компилятора должна отличаться от ошибки программы. Снимать проверку Cranelift
для сокрытия этих проблем нельзя.

### 8. Runtime не переносится вместе с компилятором

Репозиторный `runtime.o` — ELF x86-64. На macOS ARM64 даже минимальная программа
не линкуется: `unknown file type in 'runtime.o'`. В `src/aot_backend.rs:56` и
`:63` файл ищется в текущем рабочем каталоге. Установленного `plrc` недостаточно,
чтобы скомпилировать программу из произвольной папки.

Нужно определить способ поставки runtime для каждой поддерживаемой платформы:
встроенный объект подходящего target либо встроенный C-исходник с компиляцией
выбранным toolchain. Объект runtime линкуется с пользовательской программой;
одного включения C-кода в бинарник самого `plrc` недостаточно.

Отдельная проблема по исходникам: C runtime использует `long`, а язык — `I64`.
В Windows ABI `long` имеет 32 бита. Нужны `int64_t` и соответствующие форматные
макросы из `<inttypes.h>`. Windows-выполнение здесь не проверялось;
[размеры типов подтверждает документация Microsoft](https://learn.microsoft.com/en-us/cpp/cpp/data-type-ranges?view=msvc-170).

Также сейчас проверяется наличие `gcc`, хотя на Unix вызывается `cc`.
Проверять нужно выбранный инструмент; полезны `--linker` и поддержка `CC`.

### 9. Lock-файл не соответствует версии пакета

В `Cargo.toml` указана `1.0.0`, в записи самого пакета в `Cargo.lock` — `0.4.0`.
Это воспроизводимо блокирует сборку с `--locked` из свежего checkout.
Нужно обновить lock-файл вместе с версией пакета и добавить такую сборку в CI.

## Минимальная спецификация языка

До расширения синтаксиса нужно письменно решить следующие вопросы.

| Область | Предлагаемое правило для первого законченного ядра |
| --- | --- |
| Чтение исходника | Сверху вниз по столбцу, затем следующий столбец слева направо |
| Геометрия | Явно описать пустые клетки, разделение токенов, короткие строки и пустые столбцы |
| Tabs и Unicode | Выбрать единицу столбца; для первого этапа можно запретить tabs вне строк с понятной ошибкой |
| Числа | `int` = signed 64-bit, `float` = IEEE-754 binary64 |
| Преобразования | Сначала строгая проверка; преобразования типов явные |
| Условия | Только `bool`; арифметика над `bool` запрещена |
| Операторы | Унарные → умножение/деление/остаток → сложение → отношения → равенство → `&&` → `\|\|` |
| Логические операции | `&&` и `\|\|` с коротким замыканием; выбрать вертикально удобное написание |
| Сравнения | Определить, допустимы ли цепочки; сначала можно запрещать неоднозначные цепочки |
| Области видимости | Лексические блоки; явно решить shadowing и повторное объявление |
| Изменяемость | Сохранить текущее присваивание для `LT`; константы можно добавить позже |
| Функции | Явный тип результата и отдельный `unit`/`void`; предложенный синтаксис оформить как RFC |
| Возврат | Значение нужного типа на всех достижимых путях; отсутствие `RET` допустимо для `unit` |
| Точка входа | Ровно одна `main` с определённой сигнатурой; адаптер к C ABI процесса |
| Ошибки выполнения | Определённая политика деления на ноль, переполнения, неверного ввода и EOF |
| Совместимость | Разделить версию реализации и гарантии версии языка; документировать изменения |

Это предложения, а не описание уже реализованного поведения. В частности,
обычная блочная область видимости и строгий `bool` являются выбором дизайна.

## Архитектура следующего шага

```mermaid
flowchart LR
    A[Исходный .plr] --> B[Layout и SourceMap]
    B --> C[Токены с диапазонами]
    C --> D[AST с диапазонами и аннотациями]
    D --> E[Разрешение имён и проверка типов]
    E --> F[Типизированное представление]
    F --> G[Cranelift]
    G --> H[Объект и линкер]
```

Для текущих примерно 1 350 строк Rust достаточно одного crate с `lib.rs` и тонким
CLI. Нужны ясные границы между этапами; разбивать проект на множество crates пока
необязательно. `compile_source` должен возвращать результат и диагностики без
`process::exit`, чтобы им пользовались тесты, CLI и будущий language server.

### SourceMap — основа удобства Pillar

Сейчас `main` показывает лексическую ошибку в транспонированном тексте под именем
исходного `.plr`, а синтаксические ошибки используют индексы токенов. У токенов и
AST нет сохранённых исходных диапазонов.

Нужно хранить соответствие логических позиций физическим byte offsets исходника.
Вертикальное имя состоит из символов на разных строках: один обычный непрерывный
range захватывает между ними и чужой код. Полезно хранить набор исходных сегментов,
а для основного сообщения выбирать первый значимый символ. Карта должна учитывать
UTF-8, CRLF и виртуальные пробелы, появляющиеся при дополнении коротких строк.
Для редакторов дополнительно потребуется перевод в согласованную кодировку позиций.

Сначала стоит сделать правильные координаты ошибок. На этой основе появятся
переименование, переход к определению, подсветка и отладочная информация.

## Что сделает язык удобным именно как Pillar

1. **Редактирование столбцами.** Вставка символа вниз со сдвигом нужного столбца,
   добавление и удаление столбца, перемещение выражения, понятное поведение paste.
   Это нужно проверить на реальных сценариях редактирования.
2. **Связанные вертикальное и горизонтальное представления.** В MVP горизонтальный
   режим может быть предпросмотром. В проекте должен быть один авторитетный исходник;
   хранение двух независимо редактируемых копий создаёт риск расхождения.
3. **Форматтер, сохраняющий смысл.** Он должен понимать токены и комментарии.
   Обычное транспонирование с добавлением пробелов не является полноценным
   форматированием и не гарантирует побайтовый round trip.
4. **Комментарии и документация.** Указать направление действия комментария:
   логический конец строки после преобразования соответствует концу столбца.
   Сначала выбрать правило, затем добавлять `//`, блочные или doc-комментарии.
5. **Короткие удобные конструкции.** Оценивать синтаксис по высоте столбца,
   читаемости и цене вставки. Сокращения `FN`, `LT`, `RET` здесь обоснованы.
   Для терминатора `~` нужны единые примеры и объяснение назначения.
6. **Playground с двумя представлениями и примерами.** Публиковать после стабилизации
   ядра. Для запуска пользовательского кода нужны ограничения времени, памяти и
   вывода; альтернативой может стать отдельная браузерная реализация выполнения.

Для редакторских возможностей подходит
[Language Server Protocol](https://microsoft.github.io/language-server-protocol/).
Для вертикальных токенов стоит выдавать физические сегменты подсветки и проверять
возможности конкретного клиента. Стандартной подсветки регулярными выражениями
для горизонтальных языков может оказаться недостаточно.

## Какие возможности добавлять дальше

Рекомендуемый порядок после исправления ядра:

1. Строковые литералы, экранирование и вывод текста. Начать с неизменяемых строк;
   отдельно определить UTF-8, длину и владение. Поддержку динамических строк
   не следует обещать раньше решения управления памятью.
2. `&&`, `||`, `break`, `continue`, явные числовые преобразования.
3. Простая стандартная библиотека: ввод-вывод, математика, обработка EOF и ошибок
   ввода. Не кодировать каждую будущую библиотечную операцию отдельным видом AST.
   Нынешние `OUTI`/`INPI` можно сохранить как синтаксический сахар.
4. Модули и импорт: возможность разбить программу на файлы с определёнными
   правилами поиска, видимости и циклических зависимостей.
5. Массивы, затем небольшие структуры — если выбранные реальные программы
   показывают необходимость. До этого определить проверки границ и память.

Generics, классы, async, макросы, package manager, собственный оптимизатор и второй
backend можно рассматривать после появления конкретных задач, требующих их.
Полезнее сначала написать несколько законченных программ: числовую утилиту,
интерактивную игру, обработчик текста. Они покажут реальные пробелы языка.

## Инструменты, тестирование и поставка

- Вынести примеры в `examples/`; выбрать один исходный формат, второй генерировать
  или автоматически проверять на эквивалентность. README сейчас содержит `;`,
  хотя лексер принимает `~`; показанное выражение также отличается от C-примера.
- Добавить `check` без линкера, `build`, `run`, явное преобразование представления
  и `fmt`. Сначала спроектировать команды и совместимость с текущим CLI.
- Предусмотреть `--emit=tokens,ast,ir,obj`, `--color=auto|always|never` и машинный
  формат диагностик. Сообщения и результаты программы должны иметь разные потоки.
- Использовать `Path`/`PathBuf` до границы API, требующей строку; корректно сообщать
  об ошибках файлов и линкера. Временные объекты размещать в отдельном каталоге,
  не рядом с исходником и не по имени, способному совпасть с `-o`.
- Создать CI для обычных изменений: fmt, clippy, unit/integration tests и запуск
  примеров, со сборкой через `--locked`. Нынешний workflow занимается релизной сборкой и упаковкой.
- Проверять установочный архив в чистом каталоге на каждой заявленной платформе:
  наличие бинарника ещё не означает, что он способен собрать программу.
- Убрать фиксированный `runtime.o` из роли источника истины; собирать его
  воспроизводимо. Пересмотреть обязательный `mold` в Linux-конфигурации:
  либо документировать установку, либо сделать его необязательной настройкой.
- Добавить языковую справку, грамматику, таблицу возможностей, changelog,
  правила совместимости и осознанно выбрать лицензию. Файла лицензии сейчас нет;
  его выбор должен сделать автор.
- Для `build.rs` использовать Cargo `OUT_DIR`; согласовать упаковку completions
  с этим изменением. Указать поддерживаемый Rust toolchain/MSRV.

### Набор проверок, который действительно защищает язык

- Unit tests на токены, приоритеты, `EL + block`, сохранение типов и координат.
- Проверки семантики: имена, scope, типы, количество аргументов, `RET`, `main`.
- Compile-fail cases: ожидаемый код ошибки и позиция в исходном `.plr`.
- End-to-end: программа → компиляция → запуск → stdout и exit code.
- Проверки инвариантов: форматирование идемпотентно, два представления имеют
  одинаковый смысл, перенос строки CRLF не меняет программу.
- Fuzzing frontend: произвольный исходник не должен приводить к panic или
  чрезмерному расходу ресурсов. Для валидных программ полезно сравнивать
  результаты с небольшим интерпретатором проверенного AST, если такой появится.
- Для тестов выполнения ограничивать время, вывод и ресурсы процесса.

Не нужно гнаться за количеством тестов: каждый должен закреплять правило языка
или предотвращать конкретную регрессию. Успешный clippy уже сейчас не обнаруживает
ошибки типов, областей видимости и control flow.

## Последовательность работ с критериями готовности

| Этап | Изменения | Когда готово |
| --- | --- | --- |
| 1. Регрессионная база и запуск | Тестовый harness, 5 примеров, runtime под target, независимость от cwd | Установленный compiler собирает и запускает примеры из чистого каталога |
| 2. Исправления существующего синтаксиса | `EL + block`, завершение блоков после `RET`, граничные числовые литералы | Минимальные воспроизведения закреплены тестами; валидный `RET` в цикле работает |
| 3. Исходные координаты | SourceMap, spanned tokens и AST, библиотечный frontend, структурированные ошибки | Ошибки лексики и синтаксиса указывают на реальные клетки `.plr` |
| 4. Семантика | Сохранённые типы, scopes, таблица сигнатур, тип результата, проверка control flow | Проверенные неверные программы отклоняются до codegen; `float`/`bool` работают в вызовах |
| 5. Минимально полезный язык | Строки и вывод текста, логика, выход из цикла, документация | Можно написать несколько завершённых программ без обхода ограничений компилятора |
| 6. Удобство редактирования | `check/run/fmt`, LSP, операции над столбцами, горизонтальный preview | Изменение программы не требует ручного восстановления всей сетки |
| 7. Стабильная поставка | CI на заявленных ОС, smoke tests установщика, спецификация и changelog | Каждая заявленная возможность проверяется тестом; установка воспроизводима |

Этапы 3 и 4 лучше согласовать одним небольшим архитектурным планом: source spans
потребуются и для ошибок типов. Часть независимых исправлений можно выпускать
раньше. Это порядок зависимостей, а не обещание сроков.

Практический критерий законченного первого ядра: для документированного подмножества
языка правильные программы дают определённый результат, ошибочные программы
получают диагностику с исходной позицией, а поставляемый компилятор воспроизводимо
работает на всех платформах, которые перечислены как поддерживаемые.
